# Rooms: Race and Duel

**Goal:** two players meet in a room through a 6-character code or its link, then either race on
one layout drawn by the bot or each hunt the layout the other hid, the first correct proposition
winning.

## Global Constraints

- Vocabulary is `CONTEXT.md`: Room, Race, Duel, Proposition, Surrender. The second player is the
  **opponent**, never "guest" (a Guest is an account without credentials).
- Each player plays **their own `game` row**, owned by them: shots, propositions, `get_owned` and
  the game socket keep working unchanged. A room links its two games; nothing about one player's
  shots ever reaches the other but their **count**.
- Both players must be registered: every room route answers 403 to a guest, like `POST /games`.
- Room code: 6 characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (no `0 O 1 I`), unique, drawn
  server-side and retried on a unique violation; the invitation link is `/rooms/<CODE>`. A room
  holds one game per player and never expires; no rematch.
- The first correct proposition ends the room: the winner's game is solved, the other game ends
  with a new status `lost`, both layouts are revealed. A surrender ends the room the same way, the
  opponent winning. Ending is one transaction locking the room row.
- Duel priority, enforced by the server: after a player's action (a new shot or a proposition; a
  replayed shot is not one), the same player may act again only once the opponent has acted or
  `10 s × (entries that player has fired) / 36` has passed. Refused with 409 and the remaining
  milliseconds. A Race has no priority.
- API: layering of `CLAUDE.md`, migration `0009_room.sql` (after the daily's `0008`), `make prepare`,
  `make check`. Front: files ≤150 lines, i18n in both locales, `data-cy`, tsc + oxlint.
- Built on `main` once the daily is merged.

### Task 1: Rooms and Race

**Files:** `api/migrations/0009_room.sql`, `api/src/models/room_model.rs`,
`api/src/models/game_model.rs`, `api/src/repositories/room_repository.rs`,
`api/src/repositories/game_repository.rs`, `api/src/services/room_service.rs`,
`api/src/services/game_service.rs`, `api/src/errors/room_error.rs`, `api/src/dto/room_dto.rs`,
`api/src/dto/game_dto.rs`, `api/src/controllers/room_controller.rs`, `api/src/controllers/mod.rs`,
`api/tests/room.rs`, `README.md`

Migration: `room_mode` enum (`race`, `duel`), `room_status` enum (`waiting`, `composing`,
`playing`, `finished`), a `room` table (id, unique `code`, mode, status, `host_id`, nullable
`opponent_id`, nullable `winner_id`, the Duel fields of task 2 can wait for task 2, timestamps), a
nullable `game.room_id`, and `lost` added to `game_status`.

- `POST /rooms` `{mode}` creates a waiting room hosted by the caller and answers it (201).
- `GET /rooms/{code}` answers the room to its two players (mode, status, both logins, winner,
  the caller's game id once playing); to anyone else signed in, only mode, status and the host's
  login, so the link can offer to join. Unknown code: 404.
- `POST /rooms/{code}/join`: one guarded `UPDATE … WHERE opponent_id IS NULL AND host_id <> $caller`
  fills the seat; a full room or the host joining answers 409. For a Race, the same transaction
  draws one layout and creates both games with it, status `playing`; for a Duel, status
  `composing`.
- `game_service::propose` and `surrender` end the room when the game has one, as in the Global
  Constraints. `GameView` gains `room_code` (null outside a room). `GET /games` lists room games.

**Done when:** `tests/room.rs` proves a code matches the alphabet, a guest gets 403, joining twice
or as the host gets 409, a Race gives both players the same layout (compare after solving), the
first correct proposition marks the other game `lost` and the room `finished` with its winner, a
surrender makes the opponent win, and a non-member sees only the public fields.

### Task 2: Duel

**Files:** `api/migrations/0010_duel.sql`, `api/src/models/room_model.rs`,
`api/src/repositories/room_repository.rs`, `api/src/services/room_service.rs`,
`api/src/services/game_service.rs`, `api/src/errors/room_error.rs`, `api/src/dto/room_dto.rs`,
`api/src/controllers/room_controller.rs`, `api/src/controllers/game_websocket_controller.rs`,
`api/tests/duel.rs`

Migration: on `room`, the two hidden layouts (`host_layout`, `opponent_layout`, nullable JSONB),
`last_actor_id` and `last_action_at`.

- `POST /rooms/{code}/layout` `{pieces}` in a composing Duel stores the caller's layout once
  (409 on a second one). It must pass `Layout::validate` **and** hold red, blue and yellow at least
  once — the bot's rule: move it from `engine/bot.rs` into a shared check of the engine rather than
  copying it. When the second layout lands, the same transaction creates each player's game on the
  **other** player's layout, status `playing`. Neither layout is ever sent before the room ends.
- Priority: `fire` and `propose` on a Duel game lock the room row, apply the rule of the Global
  Constraints, then record `last_actor_id`/`last_action_at`. Over HTTP and over the socket alike;
  the refusal carries `retry_after_ms`.
- `GET /rooms/{code}` gains, for a playing Duel, who acted last and when the caller may act again.

**Done when:** `tests/duel.rs` proves a layout without yellow is refused with the rule broken,
each player's game holds the other's layout, an immediate second action at 18 entries fired is
refused with about 5 000 ms left (set `last_action_at` in SQL rather than sleeping), the same
action passes once the opponent acted, and a replayed shot neither counts nor is refused.

### Task 3: Live room events

**Files:** `api/src/services/game_websocket_hub.rs`, `api/src/controllers/game_websocket_controller.rs`,
`api/src/dto/game_dto.rs`, `api/tests/live.rs`

The socket of a room game also subscribes to a channel of its room (the hub is keyed by `Uuid`:
the room id is a key like a game id). On it, pushed to both players: `opponent {shots}` after the
opponent's new shot, `priority {actor, until}` after any Duel action, and the existing `game`
snapshot of each player's own game when the room ends, so the loser sees `lost` and the layout.
Never the opponent's shots themselves.

**Done when:** a live test with two players' sockets proves the opponent's count arrives after a
shot, no `shot` of the other player ever does, and both sockets get the end of the room.

### Task 4: Lobby

`front/app/rooms/[code]/_components/*`, `front/app/rooms/[code]/_viewmodels/use-room.ts`,

`front/app/i18n/locales/en.ts`, `front/app/i18n/locales/fr.ts`

- On `/play`: "Race" and "Duel" buttons create a room and open `/rooms/<code>`; a 6-character
  input (uppercased, alphabet-checked) opens a room by code.
- `/rooms/[code]`: the code, a "copy invitation link" button (`navigator.clipboard`), the players;
  a non-member sees "Join". While waiting or composing, poll `GET /rooms/{code}` every 2 s
  (`ponytail:` comment — a room channel on a socket if polling shows its limits). Once playing,
  go to `/games/<id>`.
- Signed out on a room link: send to `/login?next=/rooms/<code>`; every sign-in route honours
  `next` only when it starts with `/` and not `//`, else `/play` (no open redirect).

**Done when:** tsc and oxlint pass; by hand, with two browsers, one creates a Race, the other opens
the copied link, signs in, joins, and both land on their game.
