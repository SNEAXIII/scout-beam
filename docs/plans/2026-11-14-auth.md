# Real authentication

**Goal:** a player signs in with a login and password, with Discord or with Google, or plays as a
guest who can later sign up without losing their games.

## Global Constraints

- Vocabulary is `CONTEXT.md` (Guest, Player…); the guest model is `docs/adr/0001-guests-are-user-rows.md`.
- API layering is the one in `CLAUDE.md`: controllers → services → repositories, one file per
  domain in each layer. Auth routes live in `controllers/user_controller.rs`; the JWT codec in
  `auth/` stays table-free.
- Migrations are forward-only and new (`0005_…`, `0006_…`); never edit an applied one. Each
  changed query ships with `make prepare`. `make check` passes at the end of every API task.
- Every sign-in route answers the existing `LoginResponse` token pair; `POST /auth/refresh` and
  `POST /auth/dev-login` keep working unchanged (dev-login only with `ENV=dev`).
- No plaintext email anywhere: not in a column, a log line or an error. The provider's username
  and avatar are never stored nor shown: an OAuth account's login comes from
  `services/login_generator.rs`. Whether to keep the email in clear one day is an open question:
  only the hash for now.
- Secrets (`DISCORD_CLIENT_SECRET`, `GOOGLE_CLIENT_SECRET`, `EMAIL_PEPPER`) stay in the API and
  never reach the front or a log; `Config`'s `Debug` must not print them.
- API messages stay in French, like the existing `UserError`. Front strings go through `useI18n()`
  with keys in both `en.ts` and `fr.ts`.
- New API dependencies: `argon2`, `pbkdf2` + `sha2`, `reqwest` (rustls, json), `tower_governor`.
  No new front dependency.

### Task 1: Password accounts

**Files:** `api/migrations/0005_password.sql`, `api/src/models/user_model.rs`,
`api/src/repositories/user_repository.rs`, `api/src/services/user_service.rs`,
`api/src/services/password.rs`, `api/src/dto/user_dto.rs`, `api/src/errors/user_error.rs`,
`api/src/controllers/user_controller.rs`, `api/src/main.rs`, `api/Cargo.toml`, `api/tests/auth.rs`,
`README.md`

Add a nullable `password_hash` column to `user`. Two routes:

- `POST /auth/register` `{login, password}` creates an account and signs it in. Login rules are the
  existing ones (3–30 ASCII letters or digits, reuse `validate_alphanumeric`); the password is 8 to
  128 characters. A taken login answers 409 through `UserError::LoginAlreadyTaken`.
- `POST /auth/login` `{login, password}` signs in. An unknown login, an account with no password
  and a wrong password all answer the same 401 message, and take about the same time (verify
  against a dummy hash when there is no account).

Hash with Argon2id (the `argon2` crate's defaults), in `services/password.rs`, run under
`tokio::task::spawn_blocking`. `touch_last_login` on every sign-in, as `login_or_create` does.

Rate-limit `/auth/register`, `/auth/login` and every sign-in route added later with
`tower_governor`, keyed by `SmartIpKeyExtractor` (the API sits behind Traefik): 5 requests a
minute per IP with a burst of 5, answering 429. `main.rs` serves with
`into_make_service_with_connect_info::<SocketAddr>()`; tests send `X-Forwarded-For` so `oneshot`
calls have a key. Add both routes to the README table.

**Done when:** integration tests prove register then login returns a working token pair, a wrong
password and an unknown login get the same 401 body, a duplicate login gets 409, a 7-character
password gets 400, and a sixth login attempt in a minute from one IP gets 429.

### Task 2: Guests

**Files:** `api/migrations/0006_guest.sql`, `api/src/models/user_model.rs`,
`api/src/repositories/user_repository.rs`, `api/src/services/user_service.rs`,
`api/src/dto/user_dto.rs`, `api/src/errors/user_error.rs`, `api/src/errors/game_error.rs`,
`api/src/controllers/user_controller.rs`, `api/src/controllers/game_controller.rs`,
`api/tests/auth.rs`, `api/tests/game.rs`, `README.md`

Add `guest BOOLEAN NOT NULL DEFAULT false` to `user`, with a CHECK that a guest has no
`password_hash`. An explicit flag rather than "has no credentials", because dev-login and
`seed_user` accounts have none and are not guests.

- `POST /auth/guest` (no body, rate-limited like task 1) creates a guest with a login from
  `login_generator::unique_login` and signs it in.
- `POST /auth/register` called with a guest's bearer token turns that guest into the new account:
  same row and id, the chosen login replaces the generated one, `password_hash` set, `guest` false.
  Any other bearer (or none) creates a new account as before. A guest token on `/auth/login` is
  ignored: the existing account wins and the guest row stays as it is.
- `UserProfile` gains `guest: bool`, so the front knows.
- Guests may only play the daily (built later): `POST /games` answers 403 for a guest, with a
  French message saying an account is needed.

**Done when:** tests prove a guest gets a token and `guest: true` from `/auth/session`; registering
with that token keeps the same user id, flips `guest` to false and keeps a game inserted for it
beforehand; a guest's `POST /games` gets 403.

### Task 3: Discord and Google sign-in

**Files:** `api/migrations/0007_oauth.sql`, `api/src/config.rs`, `api/src/state.rs`,
`api/src/services/oauth_service.rs`, `api/src/services/email_hash.rs`,
`api/src/repositories/user_repository.rs`, `api/src/dto/user_dto.rs`,
`api/src/errors/user_error.rs`, `api/src/controllers/user_controller.rs`, `api/tests/oauth.rs`,
`api/tests/common/mod.rs`, `api/.env.example`, `stack.yaml`, `README.md`

Add to `user`: `discord_id TEXT UNIQUE`, `google_id TEXT UNIQUE`, `email_hash TEXT UNIQUE`,
`email_hash_version SMALLINT`, all nullable; the guest CHECK of task 2 extends to both provider ids.

Config, all optional: `DISCORD_CLIENT_ID` + `DISCORD_CLIENT_SECRET`, `GOOGLE_CLIENT_ID` +
`GOOGLE_CLIENT_SECRET` (a provider is enabled only when both are set; one without the other fails
at boot), `EMAIL_PEPPER` + `EMAIL_PEPPER_VERSION` (required as soon as one provider is enabled).
The front origin is `CORS_ALLOWED_ORIGIN`; the redirect URI is that origin followed by
`/login/callback/discord` or `/login/callback/google`, built by the API and never taken from the
request. The provider endpoints (authorize, token, profile) live in config with the real URLs as
defaults, so tests point them at a local mock.

- `GET /auth/providers` answers `{dev_login: bool, providers: [{name, authorize_url}]}` for the
  enabled providers. `authorize_url` carries client id, redirect URI, `response_type=code` and the
  scopes (`identify email` for Discord, `openid email` for Google), without `state`: the front adds
  it.
- `POST /auth/discord` and `POST /auth/google` `{code}` exchange the code with the client secret,
  read the profile (Discord `/users/@me`: `id`, `email`, `verified`; Google userinfo: `sub`,
  `email`, `email_verified`) and resolve the account, in this order:
  1. an account with that provider id signs in; if its `email_hash_version` is stale and the email
     is still verified, rehash it with the current pepper (only an existing hash, never a new one);
  2. else, with a verified email, an account with that `email_hash` gets the provider id linked —
     unless it already holds another id for that provider: 409 "compte déjà lié";
  3. else the caller's guest (bearer token, as in task 2) is converted, or a new account created,
     with a generated login, the provider id, and the email hash only if the email is verified.
- `services/email_hash.rs`: PBKDF2-HMAC-SHA256 of the trimmed, lowercased email with the pepper,
  200 000 iterations, hex. Unverified emails are never hashed: linking on one would let anyone
  capture an account by declaring its address.

A provider failure (refused code, network) answers 401 with a generic message; the provider's
answer goes to a `tracing` warning, without the email. Add the six variables to `.env.example`,
the secrets to `stack.yaml` like `scout_beam_jwt_secret`, and the routes plus a "create the
Discord and Google apps" note to the README.

**Done when:** `tests/oauth.rs`, against a mock provider served on a local port, proves: a first
sign-in creates an account with a generated login and no plaintext email in the row; a second
sign-in returns the same account; Discord then Google with the same verified email give one
account; an unverified email creates a separate one; a stale `email_hash_version` is rehashed; a
second Discord id on a linked account gets 409; a guest bearer is converted; `GET /auth/providers`
lists only configured providers.

### Task 4: Sign-in pages

**Files:** `front/app/login/page.tsx`, `front/app/login/_components/login-form.tsx`,
`front/app/login/_components/provider-buttons.tsx`, `front/app/login/_components/dev-login-form.tsx`,
`front/app/login/callback/[provider]/page.tsx`, `front/app/register/page.tsx`,
`front/app/register/_components/register-form.tsx`, `front/app/services/auth.ts`,
`front/app/lib/api.ts`, `front/app/i18n/locales/en.ts`, `front/app/i18n/locales/fr.ts`, `README.md`

`services/auth.ts` wraps the routes of tasks 1–3: `login`, `register`, `guestLogin`,
`oauthLogin(provider, code)`, `listProviders`, plus the existing `devLogin`.

- `/login`: the login/password form (`data-cy='login-form'`), a button per provider from
  `GET /auth/providers` (`data-cy='provider-discord'`, `data-cy='provider-google'`), a link to
  `/register`, and the current dev-login form only when `dev_login` is true.
- A provider button stores a random `state` (`crypto.randomUUID()`) in `sessionStorage`, then
  sends the browser to `authorize_url&state=…`.
- `/login/callback/[provider]` checks `state` against the stored one (mismatch or missing: error
  shown, nothing sent), posts the `code`, saves the tokens and goes to `/`.
- `/register`: login, password and confirmation; mismatch is caught before sending.
- `register` and `oauthLogin` send the stored bearer when the session is a guest's, so the guest is
  converted; a 401 from them must show the error, not bounce to `/login` (extend `RequestOptions`
  rather than special-casing paths).

Brand icons are absent from `lucide-react`: provider buttons carry the provider's name, no logo.
Update the README's front section (sign-in on `/login`, provider setup).

**Done when:** `pnpm exec tsc --noEmit` and `pnpm exec oxlint --type-aware` pass, and by hand with
the API up: register, sign out, sign in with the password; the provider buttons appear only for
configured providers; a callback with a forged `state` shows an error and makes no request.
